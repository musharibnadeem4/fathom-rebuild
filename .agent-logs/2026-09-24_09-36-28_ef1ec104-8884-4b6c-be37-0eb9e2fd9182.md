**Three things to double-check on Vercel specifically:**

1. **Request body size** — Vercel serverless functions cap inbound request bodies at a few MB, which a 12-minute recording would blow past instantly. I avoided this entirely: the file goes browser → Supabase Storage directly via a signed URL, never through your Next.js function, so this limit doesn't apply.
2. **Execution time** — the ingest route uses `after()` to keep transcribing/analyzing after the response is sent, with `maxDuration = 300`. **This needs at minimum a Vercel Pro plan** — Hobby hard-caps function duration at 60s regardless of `maxDuration`, and a few minutes of AssemblyAI + Gemini work won't fit in that.
3. **New env var** — `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` is now actually used (by the browser upload) for the first time; it was in your `.env.local` but unused before. Since it's `NEXT_PUBLIC_`-prefixed, Next.js inlines it **at build time**, so make sure it's set in Vercel's env vars before the build runs, not just at runtime — the same class of gotcha you hit with `DATABASE_URL`.

Yes — `scripts/seed.ts` calls the same `src/lib/pipeline.ts` functions as the upload route, not a separate implementation. Specifically it imports and calls:

- `missingPipelineEnv`, `contentTypeForExt`, `isVideoContentType`
- `createSupabaseServiceClient`, `createAssemblyAIClient`, `createGeminiClient`
- `buildStorageKey`, `uploadMediaBuffer`
- `transcribeAndDiarize`
- `analyzeTranscript`
- `finalizeMeeting`, `markMeetingFailed`

The only thing seed.ts still does itself is read the local file off disk (`readFile`/`stat`) and insert the initial `meetings` row — everything from "upload the buffer" through "write results to the DB" is the shared code in [pipeline.ts](src/lib/pipeline.ts).

The upload route (`/api/meetings/[id]/ingest/route.ts`) differs only in how the media gets into Storage before the pipeline starts: it doesn't call `uploadMediaBuffer` itself, because the browser already PUT the file directly to Supabase via the signed URL (to dodge Vercel's request body limit). It calls `probeMediaDurationSeconds` then `runIngestionPipeline`, which internally calls the same `transcribeAndDiarize` → `analyzeTranscript` → `finalizeMeeting` chain seed.ts uses — just entered from `mediaUrl` instead of a local buffer.

So: one transcribe/analyze/write implementation, two entry points (local buffer vs. already-uploaded URL) into the same shared functions.
